# 0023. Gutter interaction model and its per-editor listener cost

- Status: Proposed
- Date: 2026-11-27
- Issue: #23
- PR: #73, #78, #89

## Context
Issue #23 makes adding and previewing notes as direct as GitHub review comments (intent.md section 7). This ADR starts with the first part: a "+" button that follows the mouse in the gutter, a click that adds a note for that line, and a drag that selects a line range and opens the add dialog with it. The range bar (PR 2) and the hover preview (PR 3) add their own sections to this ADR.

The only new always-on cost is a mouse listener per editor (intent.md section 2). ADR 0009 already ruled out an `EditorFactoryListener` and anything declared in `plugin.xml` for tracking, because both run for every editor from startup. The add dialog and the saving path already exist (ADR 0005), and `CodeAnchors.fromLines` already builds an anchor from a line range.

## Decision
- **Where the listener attaches.** The marker pass of `NoteLineMarkerProvider` calls `GutterNoteService.attachGutterInteraction(document)` for project files, before the cache lookup, so a file with no notes gets the "+" too. `GutterAddNoteAttacher` finds the document's editors with `EditorFactory.editors(document, project)` and takes only `MAIN_EDITOR` and `UNTYPED` kinds (the test fixture creates `UNTYPED` editors; diff, console and preview editors are skipped). Each editor is claimed once with `putUserDataIfAbsent`, so two passes at the same time cannot attach twice, and later passes cost one user-data lookup. The listener itself is added on the EDT. Files outside the project (relative path is null) never reach the call, so those editors get no listener.
- **Lifetime.** The per-editor disposable is registered with the editor (`EditorUtil.disposeWithEditor`), and `GutterNoteService` holds one callback that disposes it. The callback and the per-editor disposable dispose each other, so closing an editor also removes the callback from the service: the service tracks only open editors and nothing accumulates per opened file. Unloading the plugin removes every listener and leaves no plugin class registered on a live editor. Disposing removes the listeners and the "+" (PR #73, review finding on callback accumulation).
- **Gutter width.** In the New UI the icon column of a file with no icons has width 0 (measured in the 2024.2 test environment: line numbers at 16, icon column at 32, width 0, growing to 18 once a renderer exists and not shrinking back). So that the first "+" does not push the code right, the attacher calls `setInitialIconAreaWidth` with the width of the "+" column. The reserved width is the icon width plus 1 px of margin on each side. The column is then always reserved in editors that have the listener, until the editor is reopened after the plugin is unloaded.
- **The "+" icon.** One line highlighter per editor carries a `GutterIconRenderer` (`AddNoteGutterRenderer`, left aligned, so it sits beside the note icon, which is right aligned). The renderer is created per line, only one exists at a time, and it uses identity for `equals` and `hashCode`, so the platform treats every move as a change and repaints. `mouseMoved` over the line numbers and the icon column (from the end of the annotation area to `iconAreaOffset` plus the larger of `iconsAreaWidth` and the "+" column width) moves it to the hovered line; it is only re-created when the line changes. Leaving the gutter, leaving the icon area, or hovering below the last line removes it. The icon area is the line numbers plus the icon column; the annotation area and the fold area are excluded. `GutterGeometry` holds the line conversion and the two hit tests so headless tests can replace them, because the headless editor has no gutter layout. The line comes from `EditorUtil.yPositionToLogicalLine`, the same conversion the gutter uses for its own clicks. A click is handled by the gutter through the renderer's click action, which reads the line from the highlighter at click time, so edits above the line cannot leave the click on a stale line.
- **Drag.** A press on the "+" (hit-tested with `getGutterRenderer(point)`) starts a drag, so pressing on a note icon or on the line numbers never does. While dragging, the editor selection follows the lines from the press line to the pointer line (clamped to the document), which is the visual feedback. Releasing on another line opens the add dialog for that inclusive range; releasing on the press line is a click and adds nothing here. The state is a small pure class (`GutterDrag`) with 0-based lines and no Swing types, so it is unit tested directly; the anchor uses 1-based lines, so the listener converts when it builds the draft. A press that ends on the same line is a click, which the gutter handles through the renderer's click action, so the listener only handles drags of two lines or more. The "+" does not move during a drag. Only the left button counts. Reading the 2024.2 gutter showed that on release it runs the click action of the icon under the pointer without comparing it with the press position, so a range drag released over another line's note icon would also open that note. The listener therefore marks the gutter component while a drag from the "+" is active, and the note icon's navigation handler ignores clicks while the mark is set. The gutter's release handler runs before ours, so the mark is still set when it matters and is cleared at the end of our release handler. Dragging back to the press line removes the selection the drag made. The "+" click action adds a note only while a drag state exists, that is, only when the press started on the "+"; the gutter runs the click action of the icon under the pointer on release, so pressing on a line number and releasing over the "+" would otherwise add a note. When a drag is released outside the icon area, the "+" is removed, because `mouseExited` is ignored during a drag and later moves over the editor body never reach the gutter listener. A range drag released over another gutter icon that is not a JNote icon (run or debug) is not blocked and still triggers that icon; it is tracked as a follow-up issue.
- **Adding.** `AddNoteAction.addNote(project, draft)` is the existing flow (non-blocking read action for the class name, then the dialog, then `NoteSaver`). The listener builds the draft on the EDT with `CodeAnchors.fromLines`, which reads only the document. `AddNoteAction.addNote` is an internal entry point that skips the selection lookup of the action. The context menu and the shortcut are untouched.
- **No I/O on the EDT.** The listener reads the document and the editor only. No DB or file access happens in any mouse handler.
- **Cost.** Moving the "+" replaces a highlighter, which makes the platform rebuild its gutter renderer cache over the document's highlighters on the EDT. The measurements, including that update with 500 other highlighters, are in the PR body (`GutterHoverCostTest`, `JNOTE_PERF=1`).

## Range bar (PR 2)
- **What is drawn.** A note with a status of OK or APPROX that covers two or more lines gets a thin vertical bar in the gutter over its range. Nothing is painted in the editor text area. Single-line notes, ORPHAN and NEEDS_RELOCATE notes get none.
- **Where the lines come from.** The marker pass already holds the notes after `NotePositions.sync`, so the bar uses the same RangeMarker-tracked lines as the icon. `RangeBarSpec.of` turns them into `(noteId, startLine, endLine)` values.
- **How it is drawn.** `RangeBars` keeps one `RangeHighlighter` per bar in the document's markup model (shared by all editors of the document) with a `LineMarkerRendererEx` at `CUSTOM` position that paints a 2 px rounded bar just right of the line number column. A `LineMarkerInfo` cannot carry a line marker renderer in 2024.2, so the bars are not part of the marker infos.
- **Threading.** The pass runs in the background and calls `RangeBars.update`, which compares with the last requested list and returns when it is equal, so passes that change nothing cost one map lookup. Otherwise it schedules the highlighter changes on the EDT; a stale scheduled change is skipped when a newer request exists. Highlighters follow edits between passes.
- **Lifetime.** Closing the last editor of a file and service disposal remove the bars. A pass over a file that is no longer a project file, or an empty note list from the cache, removes the bars of that document. A database switch does not clear them; like the icons they are replaced by the next pass, and bars are diffed by note id and lines. A request with bars is dropped when the document changed (modification stamp, because the line numbers belong to the document as it was when the pass ran) or has no editor left by the time it is applied, and the next pass asks again; dropping also clears the request record so that pass is not mistaken for "no change". An empty request removes bars and does not depend on line numbers, so it is applied even after an edit (review finding on PR #78). A newer request for the same document wins, because its own application is already scheduled. The highlighter map is touched on the EDT only, and a closed file also clears its request record so reopening redraws.
- **Known gap.** Turning off the "JNote notes" gutter icon option stops the daemon from calling the provider, so existing bars stay until the file is closed; they are registered in the document markup directly and not through marker infos. Fixing it needs a settings change hook, which is startup-adjacent work, so it is tracked as a separate issue.
- **Painting.** The bar is a 2 px rounded rectangle right of the line number column; the gutter column offsets differ per editor and UI, so they are read at paint time.

## Hover preview (PR 3)
- **Trigger.** The same per-editor listener also watches the note column of the gutter (right of the line numbers, up to the end of the icon column), where the note icon and the range bar are. A line inside the range of a note (OK or APPROX) in that column starts a preview. `GutterPreviewController` waits 400 ms after the mouse settles on a line, then shows the preview. It only acts when the line changes, so events on the same line cost one comparison. A preview that is open when the mouse moves away closes 300 ms later, which lets the mouse cross from the gutter into the preview; entering the preview cancels the close, leaving it schedules it again. Coming back to the line of the open preview keeps it. Pressing the "+" for a drag hides it.
- **Data.** `GutterNoteService.notesCovering` reads the per-file cache with `peek` (a hash lookup that never starts a load) and the RangeMarker-tracked lines (`NotePositions.sync`, a short lock and a loop over the notes of that file) and returns the notes covering the line; up to three cards are shown and the rest are counted. A cache filled from another database than the current one counts as empty until the next marker pass refills it. `CachedNote` already holds title, body, tags, AI source and the first snippet lines, so no DB or file read happens on the EDT. A file the cache has not loaded yet gives no preview and starts its load off the EDT, as for icons.
- **Popup and cards.** Entering an open preview also cancels a show scheduled for another line, so the card under the mouse is not replaced.
- **Content.** Each card shows the title, an AI badge when the note has an AI source, the tags, the body (cut at 8 lines or 500 characters by reading only that far, plain text in a read-only text area), the first snippet lines in a monospaced read-only area, and Edit, Open in Tool Window and Delete links. Labels set `html.disable` before the text is set, so no HTML view is built, because note titles and tags can arrive from an AI import and a title starting with `<html>` must not be rendered as HTML.
- **Popup.** A non-focusable `JBPopup` (no focus steal, cancels on click outside and on window deactivation) shown at the right edge of the gutter at the height of the hovered line.
- **Actions.** A card knows a note id and uid, and ids repeat across databases, so the actions are created when the popup opens and bound to the database the cached notes came from. Delete uses `NoteDeletion` on that database, Edit reads, asks and saves through a `NoteSaver` bound to it, and Open does nothing when the current database is another one. If the database was switched meanwhile, the bound database is closed and the action fails with a notification instead of touching a note with the same id in the new database. `GutterNoteActions` follows the Tool Window panel: Open calls `NoteSelection.request`; Edit reads the note and its tags on the DB thread, asks with the existing dialog on the EDT and saves through `NoteSaver.update`; Delete uses `NoteDeletion` and the same undo notification. The Tool Window panel keeps its own copy of these steps, so the panel is not touched in this PR.
- **Timing.** The delay uses the existing `AppDelayScheduler` (a scheduled executor task that hops to the EDT), so no thread waits and no Swing timer runs per editor. The close delay (300 ms) is shorter than the show delay (400 ms) so an old preview closes before a new one for another line opens, and it is long enough for the mouse to cross from the gutter into the card. A cancelled task may already sit in the executor queue, so each task re-checks its line before it runs and a stale one does nothing.
- **Card size.** The card is fixed to the preferred height of its content so the popup does not resize while open. The body text area is given the card width before that height is read; without it a line longer than the card wraps only after layout and the wrapped lines are clipped (Codex review of PR #89, covered by `NotePreviewPanelTest`).
- **Cache lifecycle kept from `FileNoteCache`.** `invalidate` only marks entries stale: the next lookup returns the old value while it reloads and calls `onChanged` only if the value differs, so a refresh does not flicker. A load that is invalidated while running is discarded and started again with the current version. A failed load is not retried until the next invalidation, so highlighting does not repeat a failure on every pass. Past a size limit the cache is refilled from scratch so files that were opened once do not pile up; a load whose entry was dropped by the limit or by `clear` has no waiter and is ignored. `clear` drops everything and is used on a database switch, where even a stale value must not be shown. The first load of a file that returns an empty list does not count as a change because there is nothing to draw. `peek` never starts a load.
- **Edit action details.** If the note was deleted between the preview and the edit, only the list is refreshed. A delete keeps the same `NoteDeletion` for the undo notification so the undo goes to the database the delete ran on. If the project is closed before an EDT callback runs, the callback is dropped and the waiting future is cancelled. Exceptions thrown inside EDT callbacks are reported by the event queue, so the test only watches the future.
- **Gutter geometry in tests.** The listener tests use a fixed layout (preview area x 10..30, icon area x 0..15) because a headless editor has no gutter layout. The test bodies live in helper functions because the JUnit3 runner treats a lambda inside a method named `test...` as a test.
- **Known limits found in the PR #89 review, tracked as issues.** The popup reads the database in a separate call from the cached notes, so a database switch between the two calls could bind the actions to another database than the cards came from. The body trim scans leading and trailing whitespace before the 500 character cap applies.
- **Actions match the note uid (PR #89 review, decided by the author).** `notes.id` is `INTEGER PRIMARY KEY` without `AUTOINCREMENT`, so after the newest note is deleted its id is given to the next new note, and an open preview could edit or delete that new note. The cards carry `uid` (already in `CachedNote`) and the preview actions take `(noteId, uid)`. The DB task checks the uid inside the same task that acts: `NoteRepository.deleteReturningTagIds(id, uid)` returns null without deleting when the stored uid differs; `NoteRepository.update` writes `WHERE id=? AND uid=?`, so a save after the dialog cannot hit a replaced note even if the note was swapped while the dialog was open; Edit reads the note and treats a uid mismatch as deleted (only the list is refreshed); Open reads the note and requests the selection only when the uid matches and the database is still the current one, so it now waits for one DB read. The Tool Window panel passes `note.uid` to `NoteDeletion.delete(id, uid)` the same way PR #68 keys its detail reads by uid.
- **`NoteDeletion` (reasons from removed comments).** It is the DB-side procedure of delete and undo and knows nothing about Swing or notifications, so it is tested with a temporary database. It holds the database used for the delete, so undo always goes back to the database the note was in. Reading the note and its tags and deleting it is one transaction; a note that is already gone gives null. If the database path changed meanwhile and that database is closed, undo fails with a "database switched" error instead of restoring into another database. `onCurrentDatabase()` is built per delete because the path can change, and that instance does the undo.

## Alternatives considered
- `EditorFactoryListener` registered in `plugin.xml`: attaches in every editor at creation, which is startup work and is what ADR 0009 rejected. Rejected.
- Attaching from the marker pass only for files that have notes: the "+" would not appear where a first note is added. Rejected.
- `EditorMouseListener` and `EditorMouseMotionListener` on the editor: whether gutter events reach them depends on the area, and the gutter's own renderer handling then has to be duplicated for clicks. Listening on the gutter component and letting it run the renderer's click action avoids both. Rejected.
- Handling the click ourselves on release: a press on a note icon would then also add a note, because we cannot tell which icon was hit without the same hit test. Rejected for the renderer's click action.
- `EditorGutterComponentEx.isInsideMarkerArea`: it is internal and measures the free-painter area in the new UI, not the icon column. Rejected for `iconAreaOffset` and `iconsAreaWidth`.
- Releasing a range drag over a non-JNote icon is not fixed here: stopping it needs the release to be consumed before the gutter dispatches it, which means registering ahead of the platform's own listener or wrapping the gutter. Both depend on platform internals, so it is split into its own issue.
- Range bars from the `LineMarkerInfo` pass: the daemon builds the highlighters from the infos and offers no hook for a line marker renderer. Rejected for `RangeBars`.
- One bar highlighter per editor: it multiplies the work per split. The document markup model is shared. Rejected.
- Background color over the range in the editor: excluded by intent.md section 7. Rejected.
- Moving the Tool Window's edit and delete steps into a shared class: it touches the panel and its tests in a feature PR. Rejected; the gutter has its own small copy.
- A preview that closes the moment the mouse leaves the gutter: the actions could not be reached. Rejected for the short close delay.
- Actions keyed by uid, option B, add `AUTOINCREMENT` through a migration so ids are never reused: a schema change for every user that touches the migration rules of ADR 0002 and intent.md. Rejected for this PR.
- Actions keyed by uid, option C, close the preview on `NotesChanged`: the smallest change, but a change that lands between the click and the DB task still races. Rejected; the uid check inside the DB task has no window.
- Reading the note again from the DB when the preview opens: it would make the popup wait on the DB thread and the issue requires the cache only. Rejected.
- Moving the "+" while dragging: the click and the drag start would then refer to different lines. Rejected.

## Consequences
- Pros
  - No startup work, no new dependency, no EDT I/O. Per event the listener converts one y coordinate and compares a line.
  - Files with no notes pay one user-data lookup per marker pass after the first.
- Cons and what we accept
  - The icon column is reserved (about 18 px in the New UI) in every project editor once the first marker pass has run, which shifts the code once after opening a file that had no icons.
  - The "+" appears only after the daemon has run a marker pass on the file, so an editor with highlighting turned off for that file has no "+" (the context menu and the shortcut still work).
  - `getIconAreaOffset`, `getIconsAreaWidth` and `getGutterRenderer(Point)` are public platform API, but the layout they describe differs between the classic and the new UI. The gutter geometry could not be checked in a headless test, so it is covered by the `runIde` check in the PR.
  - A drag selects text in the editor, and the selection stays after the dialog closes.
- Follow-up work
  - Hover preview review findings of PR #89 that were not fixed there are tracked as separate issues (see the PR).
  - The bar's x position (right of the line numbers) was chosen from the measured 2024.2 gutter layout and needs an eye check in the classic and New UI.
